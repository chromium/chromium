# Fuzzilli Profile Generation

This directory holds Fuzzilli profiles that fuzz renderer-exposed Mojo
interfaces through the MojoJS "lite" bindings. The profiles are generated by
[`mojom_fuzzilli_generator.py`](/mojo/public/tools/bindings/generators/mojom_fuzzilli_generator.py).

This document covers:

*   the workflow for using generated profiles
*   what the generator supports and what it doesn't
*   the design decisions and trade-offs behind the generated profiles

## Background

Fuzzilli is a coverage-guided JavaScript fuzzer built for JS engines. Its
defaults produce esoteric JavaScript that exercises builtins. To point it at
Mojo instead, a **profile** tells Fuzzilli:

*   which objects exist (`ILType`s and `ObjectGroup`s),
*   what the method signatures are,
*   how to construct valid values (builtins, `CodeGenerator`s, `OptionsBag`s),
*   which of its default generators and mutators to turn off.

### Terminology

*   **Primary interface**: the first interface the renderer binds, and the
    entry point of every fuzzing run. It must be provided with
    `--fuzzilli_primary_interface_name`.
*   **Secondary interfaces**: interfaces reached from the primary interface.
*   **Fuzzilli program**: JavaScript code run by the binary. Each `.js` file
*   in the corpus is saved a separate Fuzzilli program. Analogous to a
    ClusterFuzz "testcase".

## Workflow

### Using a profile

1.  Copy the generated profile and every file in `common/` into Fuzzilli's
    `Sources/FuzzilliCli/Profiles/`.
2.  Register the profile in Fuzzilli's profile dictionary in
    `Sources/FuzzilliCli/Profiles/Profile.swift`

### Adding a hand-written type to `common/`

Hand-write a type when the generator can't produce a useful one. Examples:
types with heavy validation such as `url.mojom.Url`, `[Native]` enums, and
fixed-size arrays.

1.  Define it in a `common/<Module>Types.swift` file, following the naming
    conventions in the header of
    [`common/MojoCommonProfile.swift`](common/MojoCommonProfile.swift).
2.  Add it to that module's lists (`...Builtins`, `...CodeGenerators`,
    `...ObjectGroups`, `...Enumerations`, `...OptionsBags`). These lists are
    aggregated into the `commonMojo*` lists.
3.  Add its fully qualified name (e.g. `url.mojom.Url`) to `IGNORED_TYPES` in
    the generator.

## Design decisions and trade-offs

### Profile configuration (`profile_definition.tmpl`)

#### Builtin mutators

*   **Nearly all builtin CodeGenerators are disabled.**
    *   Only these builtin generators are kept: `IntegerGenerator`,
        `StringGenerator`, `TernaryOperationGenerator`,
        `PlainFunctionGenerator`, `AsyncFunctionGenerator`, `AwaitGenerator`,
        `SubroutineReturnGenerator` and `TryCatchGenerator`.
    *   Fuzzilli would otherwise spend too much time producing random
        JavaScript code instead of fuzzing the Mojo objects provided. It would
        have access to hundreds of objects in `JavaScriptEnvironment`, making
        it unlikely that the target API is exercised.
*   **Three mutators are disabled:**
    *   `ExplorationMutator`, `ProbingMutator` and `PropertyAccessorMutator`
        are disabled.
    *   They target generic JS behavior (builtin property loads, getter/setter
        side effects) that is irrelevant to Mojo.

#### CodeGenerators

*   `MojoMethodCallGenerator` and `MojoPropertyRetrievalGenerator` select Mojo
    objects in the program environment and generate method calls and property
    retrievals, thereby creating more Mojo objects and exploring the API. They
    are the entry point for the intended execution loop. Accordingly, they have
    weights of 10000.
*   A variable is a "Mojo object" (`isTargetObject`) if its type's group is one
    of the `ObjectGroup`s registered by the profile (`mojoObjectGroups`).
*   The `findOrGenerateArguments` method, used by `MojoMethodCallGenerator`,
    has a default generation budget of 100 objects that is too small for
    complex arguments that require many types to be created. The budget has
    been raised to 1000.
*   A dedicated generator, with a weight of 5000, makes sure the callback is
    used in a meaningful way on a `CallbackRouter`. The callback always takes
    one parameter, whatever the method's arity. An unused parameter is
    harmless.
*   All type generators have a weight of 1. These are registered so that
    `findOrGenerateType` can use them.
*   Most array and map generators generate a container with only one element.
    Fuzzilli's `OperationMutator` and `VariadicInputReducer` add and remove
    inputs, so long runs produce arbitrarily long containers.

##### Issues:

*   `findOrGenerateType` crashes with no visible variables. This can happen
    when a generator is marked as `producing`, as Fuzzilli schedules such
    generators to run at the start of the program. Adding a dummy `inputs:
    .one` ensures generators using `findOrGenerateType` are never scheduled to
    populate the initial environment. Since these generators are only ran
    on-demand, it reduces the diversity of object types in the environment.
    Generators tend to only have numerous string and integer variables
    available to use at the start of the program.

#### Include every common definition

*   Every profile includes all `commonMojo*` builtins, generators, groups,
    enumerations and options bags. This is simpler than having the generator
    try to determine which definitions an interface needs.

##### Issues:

*   Although very unlikely given the weights, it is possible Fuzzilli calls
    irrelevant generators during a fuzzing campaign.
*   `common/` must be copied by hand, and `IGNORED_TYPES` must match it
    exactly.

#### Binding the primary interface

*   Some binders fail if `getRemote` is called multiple times. The failure
    persists across multiple Fuzzilli programs until the binary is restarted.
*   To ensure idempotent `getRemote` calls and resource management:
    *   `codePrefix` defines `getOrCreatePrimaryRemote()`, which binds once and
        caches the remote in `globalRemote`.
    *   `codeSuffix` closes that remote after every test case.
    *   Fuzzilli never sees or mutates the prefix and suffix.

#### `maxExecsBeforeRespawn: 50`

*   Respawns are important for restoring performance when the binary starts
    suffering from state pollution. With `maxExecsBeforeRespawn=1000`,
    execs/sec quickly plateau. With executions being slow and the respawn being
    so many executions away, fuzzing is slowed significantly.
*   A value of 50 seems to optimize between the high overhead of restarting
    Chromium and minimize state pollution.

#### Structs

*   Each struct gets:
    *   an `ILType` object listing its fields,
    *   an `ObjectGroup` with the field types,
    *   a `.constructor([...fields])` builtin registered under the struct's
        fully qualified name.
*   When `generate_fuzzing` (from `enable_mojom_fuzzer`) is set, the lite
    bindings' `struct_definition.tmpl` makes constructors take the fields as
    positional arguments. Side effect: `new Foo()` now gives fields that are
    present but `undefined`, as opposed to an object without those fields.

#### Unions

*   In MojoJS a union is an object literal where the active variant is the sole
    key (e.g. `{invalidBuffer: true}`). Builds with the GN argument
    `enable_mojom_fuzzer = true` have bindings with constructors for each union
    variant that output these object literals. Fuzzilli selects a constructor
    uniformly at random when generating the union.

#### WebIDL dictionaries

*   WebIDL dictionaries, such as `MojoCreateDataPipeOptions`, have no
    constructors. They are `OptionsBag`s with `.anySubset`. This outputs an
    object literal with some fields randomly undefined.
*   When a mutator picks an object literal, Fuzzilli runs generators from the
    `.objectLiteral` context. A generator must be available, as Fuzzilli
    crashes if a context has none. However, the builtin generators add
    properties and methods that never get used, so all builtin `.objectLiteral`
    generators are disabled and `MojoObjectLiteralNoopGenerator` is added as a
    no-op for Fuzzilli to use.

##### Issues:

*   The output is an object literal, which lacks type information, so
    Fuzzilli cannot reuse the variable.
*   Any invocation of `MojoObjectLiteralNoopGenerator` is a waste of fuzzing
    resources, since it's a no-op. However, it is cheaper than the builtin
    `.objectLiteral` generators.

#### Nullability

*   Nullable function parameters and constructor arguments are typed as
    `.either(.T, .undefined)`, emitted by the `to_fuzzilli_parameter` macro.
*   `ObjectGroup` properties do not indicate in any way they are optional.

##### Issues:

*   If Fuzzilli reads a `string?` property, it will think it is a `string`.
    Then, it may inadvertently pass `undefined` to a method that expects a real
    string when it passes in the property's value.
*   Nullable container elements are approximated by pre-filling containers with
    a few `undefined`. Consequently, Fuzzilli cannot correctly infer the type
    of container elements.


## Testing

*   `python3 mojo/golden/generate.py` regenerates
    `mojo/golden/generated/fuzzilli/` from `mojo/golden/corpus/fuzzilli/`.
*   The golden script assumes the primary interface is named `Primary`.
*   Does not run the Profile in Fuzzilli to check for compilation errors or bugs.
